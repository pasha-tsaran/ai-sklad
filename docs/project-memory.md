# Память проекта AI Support

Обновлено: 7 ноября 2026 года. Это решения проекта и отложенные работы, а не память диалогов сотрудников.

## Подтверждено пользователем

- Ручные проверки 1–7 (состояние сервера, индикатор, инструкции с фотографиями, письмо, открытие почты, отмена/возврат, защита и устойчивость) пользователь выполнил: по его сообщению всё работает.
- Сотрудники используют **классический Outlook для Windows**.
- Письма в поддержку должны отправляться **из личного почтового ящика сотрудника** после его проверки. Переход на SMTP-отправку со служебного ящика бота не выбран.
- Обычное письмо сейчас открывается через `mailto:`. Этот механизм не прикрепляет бинарные файлы автоматически.
- Пользователь просил не присылать отдельный файл письма `.eml`; не возвращать его без нового согласования.

## Отложено пользователем: вернуться позже

**Настройка HTTPS-адреса и развёртывание/расширение Windows-помощника для Outlook отложены.** Не включать эту интеграцию и не представлять её как работающую.

Цель следующего этапа: сотрудник добавляет фото в личный чат Talk, затем нажимает «Открыть письмо». Помощник под его Windows-учётной записью получает подготовленный текст и выбранные фотографии по короткоживущему разрешению, создаёт черновик в Classic Outlook и прикладывает фото. Сотрудник сам нажимает «Отправить».

Для возвращения к этапу нужны:

1. Реальный внутренний HTTPS-маршрут до backend. Сетевая папка и ссылка на библиотеку документов его не заменяют.
2. Безопасная выдача снимка черновика и фото только для текущего сотрудника/обращения: одноразовое разрешение, срок действия и проверка целостности. Не передавать на рабочие места API_TOKEN, пароль бота, его cookie или постоянные ключи.
3. Расширение существующего протокола Windows на создание письма через Outlook Object Model: CreateItem → Save → Attachments.Add → Save → Display. Не вызывать Send. При нескольких ящиках проверить правильный адрес отправителя.
4. Корпоративная подпись, GPO и пилот на одном рабочем месте. Не отключать предупреждения/защиту Outlook или политики выполнения скриптов.

Источник распространения Windows-пакета: `\\srvfile-sk\Distrib\AI_bot\Scripts`. На компьютере должна запускаться защищённая локальная копия. Подготовленный сбор имени компьютера и будущая интеграция Outlook — разные действия; наличие первого не означает готовность второго.

## Текущая работа: входящие фотографии Talk

Пользователь обнаружил отсутствие ответа после отправки фото с подписью на этапе описания. В коде входящие сообщения с файлами отбрасывались. Приём фотографии, её прочтение моделью и вложение в письмо — три отдельных возможности; не заявлять готовность всех трёх после исправления только первой.

Фотографии сотрудников — данные обращения, **не утверждённая база знаний**. Хранить и обрабатывать их только в контексте текущего сотрудника и обращения. Сохранять проверенную выдачу исходных иллюстраций из инструкций.

## Возможность распознавания скриншотов

Текущая известная базовая модель `qwen2.5:32b` текстовая. Визуальная модель/OCR и передача входящих фото в неё ещё не настроены и не проверены на живом сервере. Галочка Vision в Open WebUI сама по себе не добавляет поддержку изображений базовой модели.

Предложение для будущего подключения: отдельный этап OCR/vision на Mac Studio извлекает видимый текст, программу и код ошибки. Основной агент сохраняет нынешнюю логику и подбирает технические действия только по разрешённой базе знаний. Нечитаемые части не додумывать; отсутствие подходящей инструкции сообщать прямо. Содержимое скриншота не может изменять правила доступа или системный промпт.

Справочные первичные источники: [RFC 6068 — mailto](https://www.rfc-editor.org/rfc/rfc6068.html), [Outlook Attachments.Add](https://learn.microsoft.com/en-us/office/vba/api/outlook.attachments.add), [MailItem.Display](https://learn.microsoft.com/en-us/office/vba/api/outlook.mailitem.display), [Qwen2.5-VL](https://qwenlm.github.io/blog/qwen2.5-vl/), [Vision в Open WebUI](https://docs.openwebui.com/features/workspace/models/).


## Исправление приёма фото 7 ноября 2026 года

После выпуска 0.3.6 пользователь повторно сообщил об отсутствии ответа на фото с подписью. Подтверждена ошибка в предположении о формате REST API: Nextcloud после обработки `file_shared` выдаёт `messageType=comment`, пустой `systemMessage` и типизированный объект файла в `messageParameters`. Старые тесты использовали внутреннее имя события вместо сериализованного API-ответа и не выявили ошибку.

Исправление 0.3.7 распознаёт типизированное файловое вложение в ответе API уже проверенного личного разговора и сохраняет подпись; совместимость с прежним вариантом `file_shared` остаётся. Произвольный текст пользователя, ссылки и цитаты не становятся вложениями. Новая миграция не нужна: схема остаётся `0008`. После установки нужно отправить новое фото: старые `IGNORED` сообщения и чужая история автоматически не переигрываются.

Распознавание текста на фото, автоматическое прикрепление файлов в Outlook и HTTPS-приёмник по-прежнему не включены. Исправление приёма не означает готовность этих отложенных возможностей. Фактическая версия и журналы контейнера Debian проверяются отдельно от локальных тестов.

Первичный источник формата: [Nextcloud Talk — сериализация сообщения](https://github.com/nextcloud/spreed/blob/v23.0.1/lib/Model/Message.php#L207).

Отдельное ограничение: когда сервер уже не может прочитать файл и возвращает только локализованное уведомление с параметром `actor`, пустым `systemMessage` и без объекта файла, это не идентифицируется как фото по надёжному структурному признаку. Поддержка такой формы уведомления отдельно не подтверждена; не добавлять эвристики, которые принимают произвольные сообщения за вложение.

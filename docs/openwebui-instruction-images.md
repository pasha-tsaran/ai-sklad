# Фотографии инструкций в Open WebUI 0.11.0

Workspace Tool `show_instruction_images` показывает оригинальные иллюстрации из
утверждённого DOCX прямо в ответе Open WebUI. Он нужен для прямого чата с профилем
`ai-support`: встроенные `view_file` и `view_knowledge_file` этой версии возвращают
текст, а подпись «Иллюстрация 1» и карточка источника не являются показом картинки.

Файл инструмента: [approved_instruction_images.py](../integrations/openwebui/approved_instruction_images.py).
Это код для редактора **Рабочее пространство → Инструменты**, не команда для
терминала. Обновление Open WebUI, установка программ на Debian, пересборка
контейнеров и миграция БД приложения для этой настройки не требуются.

## Как работает

1. Модель находит подходящий документ в прикреплённой утверждённой базе знаний и
   читает его текст с условиями применения и предупреждениями.
2. Для нужных иллюстраций вызывает `show_instruction_images` с настоящим ID DOCX.
3. Инструмент проверяет принадлежность разрешённой коллекции и доступ текущего
   пользователя. Он извлекает встроенные фотографии и их альтернативные описания,
   преобразует изображения в PNG и создаёт приватные файлы в Open WebUI.
4. Инструмент отправляет событие `files`, которое Open WebUI 0.11.0 отображает как
   изображения в сообщении. Подписи возвращаются модели в служебном JSON; модель
   должна дать по ним понятное текстовое пояснение каждой показанной фотографии.

Картинки сохраняются из исходной инструкции, а не рисуются заново. Сам факт показа
не означает, что текстовая модель распознала изображение: для объяснения она
использует подготовленные описания. Каждая иллюстрация должна иметь понятное
альтернативное описание в DOCX; комплект «Инструкция-AI» подготовлен с описаниями.

Приватная загрузка не открывает файлы всему серверу. Однако изображение, отправленное
в чат, становится частью переписки: доступ к самой переписке и её дальнейшее
распространение определяются настройками Open WebUI и действиями пользователя.

## Настройка в интерфейсе

Настройку выполняет администратор Open WebUI, которому разрешено создавать инструменты.

1. Откройте **Рабочее пространство → Инструменты** и создайте новый инструмент.
2. Откройте файл
   [approved_instruction_images.py](../integrations/openwebui/approved_instruction_images.py),
   скопируйте всё его содержимое в редактор инструмента и сохраните. Не вставляйте
   этот код в сообщение чата или системный промпт модели.
3. В настройках **Valves** этого инструмента проверьте `allowed_knowledge_ids`.
   Для нашей базы знаний используется список:

   ```json
   ["85cda3aa-b854-4c26-9948-12da742277ef"]
   ```

   Это ID утверждённой коллекции, не `file_id` отдельной инструкции. При переносе
   на другой сервер укажите фактический ID новой коллекции. Не добавляйте чужие
   коллекции, чтобы обойти отказ в доступе.
4. Откройте **Рабочее пространство → Модели → ai-support**. Прикрепите к этому
   профилю утверждённую базу знаний и созданный инструмент. Не подключайте инструмент
   ко всем моделям сервера.
5. Выберите **Native** для вызова функций. Включите необходимые встроенные категории
   **База знаний / Knowledge Base** и **Файлы / Files**. Генерацию изображений для
   профиля оставьте выключенной: она не нужна для показа оригинальных инструкций.
6. Замените системный промпт полным текстом из
   [openwebui-system-prompt.txt](prompts/openwebui-system-prompt.txt) и сохраните профиль.
7. Создайте **новый сохраняемый чат** с профилем `ai-support`, чтобы проверить
   сохранённые инструменты и настройки профиля. Для этой проверки выключите
   временный режим чата.

Название и расположение переключателей зависят от языка интерфейса. Не создавайте
API-ключи и не указывайте их в коде инструмента, параметрах модели или ссылках
изображений: используется текущий пользователь Open WebUI.

## Вызов инструмента

Публичный метод — `show_instruction_images`. Модель передаёт:

| Параметр | Значение |
| --- | --- |
| `file_id` | Реальный ID прочитанного DOCX, полученный при поиске или чтении файла |
| `image_numbers` | `"1"`, `"1,2"` и другие положительные номера через запятую либо `"all"` |

Нумерация иллюстраций начинается с **1** и следует порядку изображений в исходном
DOCX. Если указаны номера `"3,1"`, картинки всё равно показываются в порядке исходного
документа: сначала первая, затем третья. За один вызов разрешено не более **6** фотографий.
Если `"all"` выбирает больше шести, инструмент возвращает `selection_required` с
данными источника и описаниями для выбора номеров, повторно проверяя доступ, и
ничего не отправляет. Вручную искать UUID сотруднику
не требуется. Модель должна найти документ
самостоятельно и передать его настоящий ID. Имя файла, ID коллекции и придуманный
UUID для `file_id` не подходят.

При успехе возвращается `status="displayed"` и `displayed=true`. Поле `source`
содержит `file_id`, `filename`, `knowledge_id` и `sha256`; элементы `images` — номер,
описание и данные созданного изображения (`number`, `caption`, `filename`, `file_id`).
Пользователь должен увидеть сами изображения и подготовленные описания, а не этот
служебный JSON. Успешный поиск документа или вызов `view_file` ещё не подтверждает
отправку фотографии. Проверяйте результат именно `show_instruction_images` и
фактическое отображение изображения. Модель должна объяснить показанные картинки
по возвращённым подписям, не повторяя уже выведенные пояснения и изображения.

При отказе возвращается `status="error"`, `displayed=false`, `code` и `message`.
Например, неверный выбор номера, отсутствие иллюстраций, неподдерживаемый документ
или отказ в доступе не являются разрешением подставить другую картинку.
Если после приватной загрузки произошёл сбой отправки события, результат
`delivery_unknown` означает, что показ не подтверждён. Не повторяйте такой вызов
автоматически: проверьте чат и повторите только по явной просьбе пользователя.
Повторные вызовы создают новые приватные копии изображений; кеш повторной выдачи
не используется.

В сохраняемом чате повторные вызовы внутри одного ответа сохраняют предыдущие
вложения и добавляют новые. Инструмент сверяет файлы текущего ответа через служебный
контекст Open WebUI; эти данные модель и пользователь не подставляют вручную.
Для временного чата такой синхронизации с сохранённой историей нет: рекомендуем
одну отправку выбранных фотографий за ответ и сохраняемый чат для проверки.

Ограничения чтения: DOCX до 30 МБ, до 60 исходных иллюстраций; одна картинка —
до 8 МБ и 16 млн пикселей, все нормализованные картинки — до 32 МБ.
Каждая встроенная иллюстрация должна иметь непустой альтернативный текст. OCR и
придумывание подписей инструментом не выполняются. Читаются иллюстрации в основном
теле DOCX; изображения из колонтитулов не извлекаются. При необходимости подготовьте
исходный DOCX перед повторной загрузкой в утверждённую коллекцию.

## Проверка без скриптов

Начните новый сохраняемый чат и отправьте обычное сообщение для уже проверенного
сценария с инструкцией № 05:

> В Adobe Acrobat PDF открывается, но при печати на HP не печатаются изображения.
> Из других программ принтер печатает нормально. Найди подходящую утверждённую
> инструкцию и покажи её первую иллюстрацию с простым объяснением.

Проверяйте следующие результаты:

- Модель действительно вызывает инструменты поиска и читает подходящий документ.
  В нашем комплекте этому сценарию соответствует инструкция № 05 с одной фотографией.
  Источник должен относиться к проблеме печати изображений из Acrobat, а не только
  содержать знакомое слово.
- Для фотографии вызывается `show_instruction_images` с реальным ID этого DOCX и
  `image_numbers="1"`. Он не подменяется вызовом `view_file` или `display_file`.
- В ответе показана настоящая картинка, а не только «Иллюстрация 1», описание либо
  карточка цитируемого DOCX. Сравните её с первой фотографией исходной инструкции.
- Подпись и объяснение соответствуют показанному изображению. Технические действия
  взяты из прочитанной утверждённой инструкции.

Для инструкции № 05 запрос второй иллюстрации должен завершиться честным отказом:
в этом исходном документе только одна фотография. Проверку нескольких существующих
иллюстраций выполняйте на другой утверждённой инструкции, где они действительно есть.
Отсутствие фотографий или ошибка доступа не должны превращаться в выдуманный совет.

Если тест не прошёл, раскройте результат вызова инструмента и проверьте сохранённые
Valves, реальный `file_id`, доступ пользователя, исходный DOCX и наличие описаний.
Ошибка чтения или доступа не доказывает, что нужной инструкции нет в базе знаний.

## Границы решения

- Поддерживаются встроенные фотографии из DOCX с описаниями. Это не универсальный
  просмотрщик PDF/XLSX и не генератор изображений.
- Инструмент действует в прямом чате Open WebUI. Его установка не подключает память
  PostgreSQL приложения, учёт попыток, отправку заявок и Nextcloud Talk.
- Debian backend имеет собственное чтение DOCX, снимки иллюстраций и выдачу файлов в
  Talk. Этот путь проверяется отдельно; Workspace Tool его не заменяет.
- Если backend передал служебную JSON Schema, действует его служебный режим.
  Модель не должна вызывать инструмент показа картинок вместо ответа по схеме.
- Реальная доступность инструмента и качество выбора инструкции проверяются на
  установленном Open WebUI 0.11.0 после настройки. Проверки кода не заменяют этот тест.

Технический контракт текущей версии подтверждён обработкой события `files` в
[socket/main.py v0.11.0](https://github.com/open-webui/open-webui/blob/v0.11.0/backend/open_webui/socket/main.py#L1056)
и отображением `type="image"` в
[ResponseMessage.svelte v0.11.0](https://github.com/open-webui/open-webui/blob/v0.11.0/src/lib/components/chat/Messages/ResponseMessage.svelte#L694).

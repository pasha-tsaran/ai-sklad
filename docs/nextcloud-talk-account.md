# Nextcloud Talk через учётную запись SkladTech-bot

В режиме `NEXTCLOUD_BACKEND=account` сотрудник пишет отдельной учётной записи
`SkladTech-bot` в личном разговоре Talk. Сервис `talk` на Debian читает новые
сообщения через HTTPS API, сохраняет их в БД и отправляет ответы с исходными
фотографиями. Регистрация webhook-бота через `occ`, входящий webhook и HTTPS-прокси
к API Debian для этого режима не требуются.

Режим предназначен только для личного разговора типа `1`, в котором находятся
ровно учётная запись бота и один сотрудник. Общие, групповые и публичные комнаты
не обрабатываются. Пустой `NEXTCLOUD_ALLOWED_ROOMS=[]` здесь включает обнаружение
таких личных разговоров, а не разрешение любых групп.

## Что подготовить

Нужны только три значения:

1. Базовый HTTPS-адрес Nextcloud, доступный с Debian, например
   `https://cloud.example.invalid` или адрес с префиксом `/nextcloud`.
2. Точный **логин** служебной учётной записи. По умолчанию используется
   `SkladTech-bot`; отображаемое имя пользователя не заменяет логин.
3. Отдельный **пароль приложения** из настроек безопасности этой учётной записи.

Адрес, логин и пароль вводятся на сервере в интерактивной настройке. Пароль
приложения не нужно присылать в чат или вставлять в команду терминала. При его
вводе символы и звёздочки не показываются. В Nextcloud у этой учётной записи должны
работать Talk и Files: Files используется для приватной передачи исходных фотографий.
Сотрудники должны иметь возможность найти учётную запись и начать с ней личный разговор.

Действующий `.env` уже должен содержать рабочие параметры PostgreSQL, API и
Open WebUI, включая `OPENWEBUI_API_KEY`, профиль `ai-support` и только утверждённую
коллекцию `85cda3aa-b854-4c26-9948-12da742277ef`. Почта сохраняет текущий режим.
Для выбранной ручной отправки настройте `MAIL_BACKEND=mailto` и адрес получателя
по [инструкции черновика письма](operator-mail-draft.md): SMTP-реквизиты не нужны.
Если пока стоит `MAIL_BACKEND=mock`, письмо остаётся тестовым.

## Установка на Debian

Команды выполняйте в SSH-сеансе Debian `192.168.10.198`, из `/opt/ai-support`.
Не подставляйте сюда Windows-путь проекта.

Сначала проверьте локальные изменения и заберите опубликованный код:

```bash
cd /opt/ai-support
git status --short
git pull --ff-only origin main
git log -1 --oneline
```

Если `git status --short` показал изменённые отслеживаемые файлы или `pull`
остановился, сохраните эти изменения и разберите причину до продолжения.
Не используйте `reset --hard` для обхода ошибки.

Запустите настройку обычным пользователем — владельцем действующего `.env`:

```bash
python3 scripts/configure_talk.py
python3 scripts/configure_talk.py --check
```

Скрипт спросит только HTTPS-адрес, логин и пароль приложения. Он сохраняет
существующие параметры PostgreSQL, API, Open WebUI, почты, комментарии и прочие
настройки. Обновляются только следующие параметры Talk:

| Параметр | Значение |
| --- | --- |
| `NEXTCLOUD_BACKEND` | `account` |
| `NEXTCLOUD_BASE_URL` | Введённый нормализованный HTTPS-адрес |
| `NEXTCLOUD_USERNAME` | Введённый логин, по умолчанию `SkladTech-bot` |
| `NEXTCLOUD_APP_PASSWORD` | Скрыто введённый пароль приложения |
| `NEXTCLOUD_ALLOWED_ROOMS` | `[]`, только автоматически обнаруженные личные разговоры |
| `NEXTCLOUD_POLL_INTERVAL_SECONDS` | `3` |
| `NEXTCLOUD_BATCH_SIZE` | `100` |

Скрипт не выводит пароль или содержимое `.env`, не выполняет shell-команды,
не создаёт резервную копию и атомарно заменяет `.env` с правами `0600`.
Обновляемые повторные параметры Talk сводятся к одной записи; неоднозначные повторы
критичных существующих параметров и незавершённые кавычки останавливают запись.
Символы `$`, кавычки и обратные слеши экранируются для Docker Compose, а не
исполняются. Ссылки вместо `.env`, переносы строк в значениях и запуск из другой
папки отклоняются. `--check` ничего не меняет, не обращается к сети и проверяет
только наличие, формат и права файла: успешная проверка не подтверждает пароль
или доступность Nextcloud. Не выводите полный `docker compose config` для проверки
пароля: он может раскрыть действующие секреты.

Сначала соберите образы, оставляя действующие сервисы работать:

```bash
sudo docker compose build api worker migrate talk
sudo docker compose run --rm --no-deps talk python -m app.talk_worker --check
sudo docker compose run --rm --no-deps talk python -m app.talk_worker --check-knowledge
```

Команда `--check` — отдельная **сетевая проверка**, в отличие от локального
`scripts/configure_talk.py --check`. Она проверяет авторизацию и доступные личные
разговоры только GET-запросами, не меняет отметки прочтения, не открывает БД,
не отправляет сообщения и не загружает файлы. В безопасном JSON-ответе ожидаются
`status=ok`, `account=authenticated`, `messages_sent=0` и `files_uploaded=0`.
`private_conversations=0` допустимо, если сотрудник ещё не начал подходящий личный
разговор; это не сквозная проверка ответа бота. При ошибке сначала исправьте доступ.

`--check-knowledge` отдельно проверяет путь Open WebUI: доступ к разрешённой
коллекции, её файлы, поиск инструкции о громкости и подсветке сканера штрихкодов и чтение
исходного документа с фотографиями. Она не пишет в БД приложения, не читает входящую
очередь Talk, не отправляет сообщения или письма и не загружает вложения в Nextcloud.
Ожидаются `status=ok`, `read_only=true`, `approved_files` больше нуля,
`instruction_found=true` и ненулевое `illustrations` для подготовленной инструкции.
Одного `status=ok` при `instruction_found=false` недостаточно для проверки этого
сценария. При ошибке выводятся только `stage`, `error_code` и `http_status`,
без ключа API, текста документа и тела ответа сервера.

Этот выпуск исправляет чтение списка файлов Open WebUI 0.11: сведения о базе
могут возвращать `files: null`, а сами файлы читаются через отдельный постраничный
API той же разрешённой коллекции. Это не означает, что коллекцию нужно создавать
или загружать заново. Наличие `knowledge_configured=true` в readiness подтверждает
настройку ID, но не заменяет эту проверку.

Текущий выпуск **0.3.12** использует существующую схему **`0009`**. Таблица приватных
указателей на помогшие инструкции добавлена в 0.3.8; новая миграция для 0.3.12 не нужна.
Если на сервере уже применена `0009`, получите код, соберите и пересоздайте только
сервисы приложения:

```bash
git pull --ff-only origin main
sudo docker compose build api worker talk
sudo docker compose up -d --no-deps --force-recreate api worker talk
sudo docker compose exec talk python -c "from app.main import app; print(app.version)"
```

Если это первое подключение Talk или на сервере ещё `0008` либо более старая схема,
после сборки остановите обработку сообщений и примените миграцию:

```bash
sudo docker compose stop api worker talk
sudo docker compose run --rm migrate
```

Миграция должна завершиться с кодом `0`. Версия `0005` добавляет устойчивое
состояние учётной записи Talk, курсоры комнат и входящую очередь; `0006` — профиль
участника и служебное состояние обработки; `0007` — одноразовые запросы имени компьютера.
`0008` — ссылки на входящие фотографии и отметка в обращении; `0009` — приватные
указатели на подтверждённые успешные инструкции. Текущая вершина схемы — `0009`;
при обновлении с `0008` миграцию нужно выполнить. Существующие
данные сохраняются. Не запускайте `down -v`.

Запустите три сервиса:

```bash
sudo docker compose up -d --no-deps --force-recreate api worker talk
sudo docker compose exec api alembic current
sudo docker compose exec talk python -c "from app.main import app; print(app.version)"
sudo docker compose ps -a
curl -fsS http://127.0.0.1:8000/health/ready
sudo docker compose logs --tail=100 talk
```

Ожидаются `0009 (head)` и версия работающего Talk **`0.3.12`**.

После загрузки обновлённых файлов `01`, `37` и `38` в разрешённую коллекцию
примените запрошенные переименования и удаление ошибочной инструкции `33`.
Команда сначала доступна для просмотра плана.

```bash
sudo docker compose exec -T talk python -m scripts.update_scanner_knowledge
sudo docker compose exec -T talk python -m scripts.update_scanner_knowledge --apply
```

Результат применения должен содержать `verified: true` и три имени без `ИТ_`.
Если новые версии уже загружены, команда удаляет старые ссылки на файлы с префиксом.
Скрипт работает с коллекцией `85cda3aa-b854-4c26-9948-12da742277ef` и проверяет
её совпадение с настройкой сервера перед изменениями.

Явное указание `talk` запускает этот сервис даже с его Compose-профилем `talk`.
Его команда — `python -m app.talk_worker`. `api` и `worker` продолжают обслуживать
приложение. Readiness показывает режим `nextcloud=account` и проверяет БД;
сам по себе ответ `status=ok` не доказывает успешную авторизацию или переписку в Talk.
Для первой сборки серверу нужен доступ к реестрам образов и источникам зависимостей.

## Первое включение и перезапуск

При первой активации сохраняется граница времени для данного сервера Nextcloud
и фактического пользователя служебной учётной записи. Предпочитается время из
HTTP-заголовка Nextcloud `Date`, округлённое вниз до целой секунды.
Сообщения со временем строго раньше этой границы не становятся новыми вопросами.
После включения сотрудник должен отправить **новое сообщение**; старое непрочитанное
сообщение до активации не является таким тестом.

При обнаружении личного разговора чтение идёт от старых сообщений к новым
ограниченными страницами. Курсор не прыгает сразу к последнему сообщению:
это сохраняет первый новый вопрос, появившийся во время запуска. Входящее сообщение
и новый курсор записываются одной транзакцией, повтор той же пары комнаты и ID
сообщения не создаёт второй вопрос. После перезапуска курсоры и очередь берутся
из PostgreSQL, граница активации не начинается заново.

Если по тому же адресу Nextcloud авторизуется другой фактический пользователь,
прежняя учётная запись Talk и её комнаты отключаются. Старая очередь и состояние
сохраняются для проверки, но не пересылаются новой учётной записи; обратное
переключение не включает старую обработку автоматически. Замена пароля приложения
того же пользователя не должна создавать новую границу активации.

Перед отправкой текста или фотографии снова проверяется, что это личный разговор
ровно с ожидаемым сотрудником и служебной учётной записью. Для технических блоков
также повторно проверяются принадлежность текущей утверждённой коллекции и хеш
источника; удаление, изменение файла или отзыв доступа приостанавливают отправку.
Продолжение инструкции перечитывает и проверяет источник заново. Изменение состава
участников останавливает отправку; переход в группу не расширяет доступ.

## Профиль и текущее рабочее место

После выбора письма в поддержку бот показывает **ФИО и компьютер**. Имя берётся
из проверенного профиля участника текущего личного разговора Nextcloud; это не
чтение ФИО из Windows. Проверьте имя и при необходимости исправьте. Заголовка
«Данные профиля Nextcloud» и логина в карточке и письме нет. Внутренний ID остаётся
привязкой к проверенному сотруднику и не расширяет доступ к другим разговорам.

Имя компьютера используется только из текущего обращения: сотрудник сообщает его
вручную либо передаёт через заранее установленный корпоративный обработчик ссылки.
Прошлое рабочее место автоматически не переносится: сотрудник может
пересесть за другой компьютер. Если актуального имени нет, карточка показывает
«Не определён» и задаётся один вопрос о текущем компьютере. Ни IP, ни имя контейнера
Debian не являются подтверждённым именем устройства сотрудника.

Необязательный Windows-модуль включается только после подготовки внутреннего HTTPS
callback и GPO-развёртывания пакета из `\\srvfile-sk\Distrib\AI_bot\Scripts`.
По умолчанию `DEVICE_COLLECTION_BASE_URL` пуст и ссылки сбора не предлагаются.
Readiness `device_collection_configured` подтверждает только наличие настройки;
успешное прохождение через прокси и Windows проверяется на пилоте отдельно.
При включении бот предлагает одноразовую ссылку, если текущий компьютер неизвестен;
ручной ввод остаётся запасным вариантом. Подробнее:
[получение имени компьютера через GPO](windows-device-collection.md).
HTTPS-приёмник и расширение помощника для Classic Outlook отложены пользователем;
это обновление их не включает и не требует изменения Windows-скриптов.

## Входящие фотографии сотрудников

Выпуск **0.3.7** исправляет разбор фактического REST-ответа Talk: у обычного
фото `messageType=comment`, пустой `systemMessage`, а описание файла остаётся
в типизированном параметре `messageParameters.file`. Вариант с явным
`file_shared` также поддерживается. Произвольные ссылки и rich-object параметры
не считаются фотографиями сотрудника. В текущем выпуске применяется схема **`0009`**.

В личном разговоре поддерживается приём фото **JPEG/PNG** с подписью. Подпись идёт
в обычную обработку текста, включая этап подробного описания письма. Если фото пришло
без подписи, бот подтверждает приём и просит описать проблему словами. Неподдерживаемое
вложение получает явный ответ, вместо молчаливого пропуска.

Сохраняются только проверенный идентификатор/метаданные сообщения Talk, подпись
и отметка наличия фото. Файл остаётся в Nextcloud: основной путь не скачивает
и не сохраняет его байты автоматически. Vision/OCR не подключены, поэтому бот
не заявляет, что прочитал изображение. Это данные текущего сотрудника и обращения,
а не утверждённая база знаний. Выдача исходных фотографий из инструкций сохраняется.

Ручная проверка: отправьте JPEG/PNG с описанием — текст должен получить ответ;
затем фото без подписи — подтверждение и просьбу описать. Проверьте неподдерживаемый
формат: вместо игнорирования должно прийти сообщение об ограничении.
После обновления отправьте новое фото: ранее проигнорированная история не повторяется.

## Проверка сотрудником

В Nextcloud Talk найдите `SkladTech-bot`, откройте **личный** разговор и после
запуска сервиса отправьте новое сообщение:

> У сканера штрихкодов нужно уменьшить громкость и настроить подсветку.

Проверьте, что получены действия из утверждённой инструкции и соответствующие
исходные фотографии с подписями. Текст шага идёт перед своей фотографией;
за один этап показывается не более шести подходящих фотографий, продолжение
выдаётся после подтверждения прогресса. Не нужны UUID, номера фото или команда
«покажи изображения». Для этого вопроса проверяется материал 37 с настроечными
штрихкодами и текстовым пояснением к нужным кодам.

Затем проверьте несколько независимых свойств:

- «Настройка сканера ШК» сначала получает короткий вопрос о цели настройки;
  «Сканер уже подключён. Мне надо его настроить» не запускает подключение заново.
- «Не работает сканер» уточняет тип устройства — штрихкодов или документов/планшетный.
  Следующий вопрос помогает понять симптом или цель настройки.
- «Настроить луч сканера и громкость» после уточнения типа ведёт к материалу 37.
  Модель оборудования у пользователя запрашивать не требуется.
- Общий вопрос о принтере уточняет тип — документы А4, стационарный термопринтер
  или мобильный термопринтер.
- Во время выдачи нескольких блоков отправьте новый вопрос. После обнаружения
  сообщения оставшаяся выдача приостанавливается, и бот обрабатывает новый запрос.
  Затем «закончи предыдущий ответ» возобновляет только оставшиеся текст/фото;
  уже доставленные блоки не повторяются. Уже принятый Talk блок отозвать нельзя.
- «Готово» продолжает применимую инструкцию по подтверждённому прогрессу.
- Приветствие или благодарность получают обычный ответ и сохраняют текущий шаг.
- Просьба искать в чужих базах знаний не расширяет утверждённый набор источников.
- Вопрос без ответа в утверждённой базе получает честное сообщение об отсутствии
  инструкции; ошибка доступа отдельно не выдаётся за отсутствие документа.
- Другой сотрудник пишет в собственный личный разговор и не получает чужую историю.
- В группе бот не начинает отвечать как в личном разговоре.

Отдельное «Привет», «Здравствуйте» или «Спасибо» обрабатывается готовым ответом
без обращения к модели и базе знаний. Реплика «Здравствуйте, сканер не работает»
остаётся техническим вопросом и проходит обычную проверку источника. Это ускоряет
простые реплики, но не задаёт обещания времени ответа всей системы.

Технические блоки в Talk и Open WebUI формирует один общий механизм: сохраняются
тот же исходный текст шагов, условия и предупреждения, подписи и порядок исходных
фотографий. В Talk эти текстовые блоки и фото приходят отдельными последовательными
сообщениями. Совпадение расположения пиксель в пиксель или дословное совпадение
каждой свободной разговорной фразы модели не гарантируется. Проверяются источник,
порядок действий, фотографии, приватность и сохранение состояния.

Если нужна поддержка специалиста, бот предлагает выбор:

- **1** — оформить письмо в техническую поддержку и перейти к форме.
- **2** — продолжить диалог с ботом без отправки заявки.

Можно ответить словами. При ожидании формы «Отмена» или «2» снимает ожидание
формы и возвращает к боту. Если сохранился применимый утверждённый источник,
продолжается тот же шаг после повторной проверки. Если источника нет или он
изменился, бот не придумывает инструкцию и возвращается к уточнению проблемы
либо сообщает о невозможности проверки. Эта отмена поддерживает и обращение,
оставшееся в ожидании формы после предыдущего выпуска; вручную править БД не нужно.

Обычная реплика после предложения выбора не открывает форму сама. Например,
«подключить поблютуз» продолжает технический вопрос, а «А если подключить по ви фи?»
меняет способ подключения в поиске, сохраняя контекст принтера и ТСД. Bluetooth при
этом не остаётся вторым обязательным условием. Письмо не оформляется без явного
выбора **1**/просьбы оформить обращение или переданного набора полей письма.

Технический вопрос вместо запрошенных компьютера или ФИО возвращает к диалогу.
Фразы «другой вопрос», «а если…» и другие явные сигналы прерывания останавливают
сбор даже на теме/описании. Обычное «Как подключить принтер?» после запроса темы
может быть самой темой письма и сохраняется буквально. Поля незавершённой формы
не используются как сведения об оборудовании или поисковый запрос.

После выбора **1** проверьте ФИО и текущий компьютер в карточке и дополните
недостающее. Далее бот отдельно спрашивает тему письма, затем подробное описание.
Один ответ о теме ещё не создаёт черновик. В Talk подробное описание обязательно
и вводится сотрудником; первоначальная проблема не заменяет его автоматически.
Описание можно написать своими словами, без подписей полей:

```text
Проводной сканер громко пищит после каждого считывания.
Нужно уменьшить звук, сохранив подтверждение успешного сканирования.
```

Старые формы с четырьмя или пятью строками, включая логин, остаются совместимыми,
но логин больше не показывается и не запрашивается. После четырёх строк без описания
бот спросит описание; пять строк с явным описанием могут завершить сбор сразу.
Сведения проверяются по сообщению, недостающее уточняется по одному вопросу.
Пока сбор продолжается, тему или описание можно исправить явным полем
`Тема: ...` или `Описание: ...`; **«Отмена»** или **2** возвращают к боту.
В режиме `MAIL_BACKEND=mailto`
это готовит письмо, а не отправляет его. В чате показываются получатель, тема
`[AI-Support] <тема проблемы>` без UUID и полный текст. Тема есть только в заголовке
с одним префиксом; тело начинается введённым описанием и заканчивается ФИО и компьютером,
без повторённой темы и блока «Исходная проблема». `.eml` не прикладывается.
Ссылка **«Открыть письмо в почте»** содержит полное тело для коротких данных.
Для длинного текста она открывает получателя и тему; полное тело нужно скопировать
из сообщения бота. Если сама тема слишком длинна для ссылки, в ней остаётся только
`[AI-Support]`, и нужно скопировать также полную тему. Видимый черновик не сокращается.
Режим и адрес задаются `python3 scripts/configure_mail_drafts.py`.
Пользователь нажимает ссылку, проверяет письмо и отправляет его в техническую
поддержку **из своего почтового ящика**. Готовое письмо можно исправить в почтовом клиенте.
При наличии входящих фото бот напоминает прикрепить их вручную: `mailto:` не добавляет
вложения. Пользователь сохраняет нужные фото из Talk/Nextcloud и добавляет их в Classic
Outlook перед отправкой. Автоматическое прикрепление отложено вместе с HTTPS/Windows-интеграцией.
Сервер не запускает Outlook на рабочем устройстве автоматически. SMTP-логин
и пароль на Debian не нужны.
Подробнее: [ручная отправка письма](operator-mail-draft.md).

## Свободная речь и повтор помогшей инструкции

### Неоднозначный запрос и прерывание ответа

До подбора действий бот выясняет тип устройства и цель слишком общей настройки.
Для сканера уточняется считывание штрихкодов либо сканирование документов, для
принтера — документы А4, стационарная или мобильная термопечать. Вопросы о модели
оборудования убраны из опроса сотрудника. Сведения, которые он сообщил сам,
учитываются вместе с условиями применения найденной инструкции.

Короткий вопрос должен помогать выбрать тип, нужную настройку или наблюдаемую
ошибку. Сообщение о подключённом сканере учитывается как условие для дальнейшей
настройки. Для громкости, звукового сигнала, подсветки, яркости луча и базовой
настройки используется материал 37 с исходными настроечными штрихкодами.

Все указанные пользователем инструкции 01, 37 и 38 доступны для подбора в
разрешённой коллекции. При загрузке используются имена без `ИТ_`. Поиск также
поддерживает прежние имена файлов в пределах той же области знаний.
Ошибочная инструкция `33_Сканер штрихкодов в базе АДРЕС.docx` отозвана.
Проверка отзыва охватывает новые результаты, прежние успешные указатели и
сохранённые блоки доставки. Фактическое удаление 33 и обновление файлов в живой
коллекции подтверждаются после применения изменений в Open WebUI.

При поступлении нового сообщения опрос Talk сохраняет его в очереди. Неотправленная
часть текущего ответа приостанавливается на границе следующей отправки, чтобы
сначала обработать новый запрос. Отправленный или уже принятый сервером блок
не отзывается. Оставшиеся текстовые блоки и исходные фотографии сохраняют порядок
и место остановки, включая перезапуск сервиса. Попросите «продолжай предыдущий
ответ» или «закончи предыдущий ответ», чтобы получить остаток без повторения
уже доставленных частей. Это отличается от «Готово», подтверждающего выполнение
обычного шага. Перед продолжением остаётся обязательной проверка утверждённого
оригинала и его доступности в той же разрешённой базе.

Неопределённая внешняя доставка `UNKNOWN` по-прежнему не повторяется автоматически.
Пауза ответа не даёт права обходить эту защиту или получать данные другого сотрудника.

### Поиск и подтверждённые повторы

Вопрос не должен дословно повторять название документа. Поиск учитывает обычные
формулировки, формы слов, сокращения и очевидные опечатки. Если выбор по фрагментам
неоднозначен, модель может выбрать только ID из разрешённых результатов и привести
проверяемую цитату; произвольные технические действия не генерируются. Перед выдачей
читается оригинал. Явно названные подключение, модель и версия должны соответствовать
источнику: инструкция Bluetooth не заменяет запрошенный Wi-Fi.

Новый технический вопрос или уточнение на этапе выбора «1 — письмо / 2 — бот»
возвращает к подбору инструкции без заполнения формы. Правила прерывания уже
открытой формы описаны выше; обычные тема и описание остаются буквальным текстом.
«Не вижу эту кнопку» или «застрял на этом шаге» сохраняют текущую
инструкцию и подходящую исходную фотографию. Явное «всё заработало» подтверждает успех;
неоднозначное «да», «готово» или просьба продолжить не обучают кэш как успешное решение.

Для понимания и поиска нормализуются известные варианты названий: «ВИ ФИ», «вифи»,
«вай фай» и Wi-Fi; «блютуз», «блютус», «поблютуз» и Bluetooth; «форти гейт» и
FortiGate; «фортиклиент» и FortiClient; «некст клауд толк» и Nextcloud Talk.
Nextcloud без Talk остаётся отдельным названием. Это ограниченный словарь алиасов,
не произвольная транслитерация: обычное «нет толка» не становится запросом о Talk.
Алиасы не объединяют разные продукты, модели или подключения. Исходные сообщения
сотрудника и текст его письма не переписываются.

Ускорение повторных вопросов включается только после явной положительной обратной
связи. В `successful_retrievals` сохраняются хеши вопроса, области знаний и технического
контекста, привязка к сотруднику/обращению, указатель источника и срок действия.
Сырые вопросы, готовые ответы, фотографии и поля формы в эту таблицу не копируются.
При повторе того же вопроса тем же сотрудником бот сначала проверяет указатель,
текущее членство документа в разрешённой базе и SHA-256 оригинала. Изменённый,
удалённый, недоступный или исключённый источник не выдаётся из старого результата.
Другие сотрудники не используют чужую историю. Срок задаёт `MEMORY_RETENTION_DAYS`.
Это сохранение подтверждённого результата поиска, не переобучение весов модели.

Для ручной приёмки используйте ваши реальные формулировки, например «как подключить
принтер к ТСД» и уточнение «мобильный принтер к ТСД по Wi-Fi». Подходящая инструкция
должна существовать в разрешённой базе; при её отсутствии ожидается честное сообщение,
а не предположение о подключении. Для существующей инструкции проверьте текст перед
соответствующим фото, затем явное «помогло», повтор вопроса и актуальность источника.
Отдельно отправьте два вопроса подряд и проверьте последовательные ответы без потери
второго сообщения. Локальные тесты не заменяют эту проверку на вашем Nextcloud.

## Ошибки доставки

Сетевой тайм-аут или прерывание неоднозначного POST могут оставить доставку
в состоянии `UNKNOWN`: сервер мог уже принять сообщение. Автоматического
повторного POST нет. Неразрешённая доставка блокирует следующие сообщения
данной комнаты, но не других сотрудников. Входящая обработка `RUNNING` сохраняет
порядок сообщений. Исчерпанная генерация `FAILED` получает один сохранённый ответ
об ошибке и перестаёт навсегда блокировать последующие вопросы. Это не повтор
неоднозначного внешнего POST.

Исходящая очередь привязана к конкретной учётной записи, а не только к токену
комнаты. После рестарта записи `SENDING` текущего фактического пользователя на
данном сервере переходят в `UNKNOWN`, а не отправляются повторно. Очередь другого
сервера, другой учётной записи и прежнего webhook-режима не присваивается текущему
боту. Прерванная генерация ответа, ещё не отправленного наружу, может безопасно
повториться до установленного лимита; это не повтор неоднозначной доставки.

Список неопределённых доставок и неудачной входящей обработки без текстов переписки:

```bash
sudo docker compose exec worker python -m app.deliveries talk
```

Сначала проверьте фактическую доставку в Talk. Только после проверки используйте
описанные в [README](../README.md#неопределённая-доставка) действия `mark-sent`
или `retry`; слепой повтор может дублировать текст или фото.

## Нативный индикатор «печатает»

В выпуске **0.3.12** сохранён штатный индикатор Talk из 0.3.4,
через внутренний signaling или настроенный HPB по WSS. Для него используется
собственная изолированная сессия, а состав личного разговора проверяется повторно.
Настройка приватности индикатора Talk соблюдается. Индикатор прекращается после
обработки; недоступность signaling не блокирует основной ответ.

Обычные сообщения «Готовлю ответ…», их удаление и замена служебной строкой
больше не используются. Старые отметки «Message deleted» в истории не удаляются.
Устанавливать программу на рабочее место сотрудника не нужно.

После запуска выполните проверку настроек только чтением:

```bash
sudo docker compose exec talk python -m app.talk_worker --check-typing
```

Она читает режим signaling и настройки доступности/приватности, не входит в разговор,
не отправляет индикатор или сообщение и не выводит пароль, ticket или токены сессии.
Успешная диагностика не заменяет проверку в вашем Talk Desktop: задайте новый вопрос
о громкости сканера штрихкодов и проверьте штатный индикатор во время подготовки,
последующий ответ и исходные фотографии. В истории не должно появляться нового
служебного сообщения или отметки его удаления. Если приватность скрывает индикатор
либо signaling недоступен, ответ и фотографии всё равно должны приходить.

## Замеры этапов

В журнале `talk` события `talk.turn_completed` и `talk.turn_failed` содержат
числовые `total_ms`, `timings_ms`, `stage_calls`, количество блоков, маршрут
и безопасный код ошибки. `cache_hit` показывает использование подтверждённого
указателя на инструкцию; это не означает пропуск проверки доступа или SHA-256.
Этапы включают `model_api`, `search`, `read`, `verify`,
`route` и `persist`, если соответствующая работа выполнялась. Времена вложенных
этапов не складываются поверх общего времени; `model_api` включает сетевой вызов
Open WebUI, а не только генерацию самой моделью. Этот замер обработки вопроса не
измеряет отдельную последующую доставку очереди или появление фотографии на экране.

В эти события не добавляются вопрос, текст ответа, пароль, ключ API, ID сотрудника,
комнаты или файла. Ошибка диагностики не должна менять утверждённый ответ.
При ошибке БД выводятся только разрешённые машинные коды (`db_sqlstate`,
`db_constraint` или `db_sqlite_code`), без SQL и значений параметров. Событие
успешной обработки публикуется после фиксации транзакции.
Просмотр журнала выполняется командой `sudo docker compose logs --tail=100 talk`;
числа помогают искать задержку, но не заменяют проверку настоящего ответа и фото.

## Сетевой доступ

В рабочем режиме Debian нужны исходящие HTTPS-соединения к Nextcloud и
`https://ai.collant.ru` и внутренние DNS/NTP. Для `MAIL_BACKEND=mailto` серверу
не требуется доступ к SMTP: письмо отправляет почтовый клиент пользователя.
Для HTTPS обычно используется порт `443`; если адрес содержит другой порт,
нужен доступ к нему. Входящий доступ Nextcloud к Debian и публикация порта `8000`
для `account` не нужны. Open WebUI продолжает обращаться к моделям на Mac Studio;
прямое подключение Talk worker к Mac Studio не требуется.

Настройка не меняет профиль модели, системный промпт, документы или область знаний.
Переустанавливать пользовательский Tool и Filter в интерфейсе Open WebUI для
этого подключения Talk не нужно: общие функции представления входят в backend.
Окончательная приёмка требует действующего URL и пароля приложения, введённых
на сервере, и реальных новых сообщений в Talk. Локальные тесты с подменённым HTTP
не заменяют эту проверку.

Справка по [экранированию переменных Docker Compose](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/#env-file-syntax).

# Письмо в поддержку: карточка и открытие почты

Режим `MAIL_BACKEND=mailto` не подключает сервер к почтовому ящику и не отправляет
письма автоматически. После заполнения формы бот готовит письмо с данными обращения
и передаёт его сотруднику в текущем личном разговоре Talk. Сотрудник открывает
черновик в своей почтовой программе, проверяет его и сам нажимает **«Отправить»**.
Файлы `.eml` не создаются и не прикладываются.

SMTP-сервер, логин и пароль для этого режима не нужны. Отправитель выбирается
почтовым клиентом пользователя. Получатель берётся только из серверного
`SUPPORT_EMAIL`, а не из сообщения сотрудника или ответа модели.

## Настройка на Debian

Для уже работающей установки Talk сначала получите опубликованный код и соберите
образы, оставляя действующие контейнеры работать:

```bash
cd /opt/ai-support
git status --short
git pull --ff-only origin main
sudo docker compose build api worker migrate talk
```

При локальных изменениях отслеживаемых файлов или ошибке `pull` сначала разберите
их причину. Не заменяйте действующий `.env` файлом примера.

Включите подготовку писем отдельной командой. Она спросит адрес получателя:

```bash
python3 scripts/configure_mail_drafts.py
python3 scripts/configure_mail_drafts.py --check
```

Для теста введите свой реальный email. Скрипт атомарно сохраняет только два
параметра в существующем `.env`, убирает их дубликаты и оставляет остальные
настройки без изменений. Пароли не выводятся, SMTP не используется:

```dotenv
MAIL_BACKEND=mailto
SUPPORT_EMAIL=your.name@collant.ru
```

`your.name@collant.ru` — образец: **для проверки укажите свой реальный адрес**.
Это адрес получателя черновика, а не пароль и не настройка отправителя.
Он вводится локально на сервере. Остальные строки, особенно PostgreSQL, API,
Open WebUI и Nextcloud, оставьте как есть. Не выводите `.env` целиком в чат.

При ручной настройке эти же строки можно изменить в `nano .env`:
**Ctrl+O**, **Enter**, затем **Ctrl+X**. `--check` только читает настройки
и не открывает сеть или почтовую программу.
Выпуск **0.3.10** требует схему **`0009`** для приватных указателей на инструкции,
которые сотрудник явно оценил как помогшие. Она применяется и при выключенном
Windows-модуле. Если `0009` уже применена,
после успешной сборки переходите сразу к пересозданию сервисов ниже.
Если сервер ещё на `0008` или более старой схеме, сначала остановите
сервисы приложения и примените миграцию:

```bash
sudo docker compose stop api worker talk
sudo docker compose run --rm migrate
```

Продолжайте только после завершения миграции с кодом `0`. Для уже работающей БД
примените новые настройки только к сервисам приложения:

```bash
sudo docker compose up -d --no-deps --force-recreate api worker talk
sudo docker compose exec api alembic current
sudo docker compose exec talk python -c "from app.main import app; print(app.version)"
curl -fsS http://127.0.0.1:8000/health/ready
sudo docker compose logs --tail=100 talk
```

В readiness ожидается `mail=mailto`. Это показывает выбранный режим, но не
подтверждает работу почтовой программы на устройстве сотрудника. База данных
и её том не пересоздаются. Ожидаются схема **`0009 (head)`** и версия Talk **`0.3.10`**;
при обновлении с `0008` миграцию нужно выполнить. Обновлять Open WebUI, переустанавливать
Tool/Filter, менять системный промпт или загруженные инструкции не требуется.
Обновлять Windows-скрипты для этого исправления также не требуется.

## Выбор в разговоре

Когда пользователь просит специалиста или подтверждённого решения недостаточно,
бот предлагает варианты:

- **1** — оформить письмо в техническую поддержку.
- **2** — продолжить диалог с ботом.

После выбора **1** бот показывает карточку с **ФИО и компьютером**. Имя берётся
из проверенного профиля участника текущего личного разговора Nextcloud, а не
считывается из Windows. Проверьте ФИО и при необходимости исправьте его.
Заголовок «Данные профиля Nextcloud» и логин не включаются ни в карточку,
ни в письмо. Внутренний ID используется только для привязки к проверенному сотруднику.

Компьютер подставляется только из данных **текущего обращения**: явного сообщения
сотрудника либо завершённого одноразового сбора через корпоративный обработчик ссылки.
Имя из прошлой заявки не переносится: рабочее место может измениться. Если актуального
имени нет, карточка показывает **«Не определён»**, и бот задаёт один вопрос об
используемом сейчас компьютере. Например, можно ответить `terminal76-sk`.
Обычный Talk API не передаёт имя компьютера Windows; IP, имя Debian и догадка
модели его не заменяют. Сам выбор поддержки ещё не создаёт и не отправляет письмо.
В ожидании формы можно написать **«Отмена»** или **«2»**. Бот снимает ожидание формы
и возвращается к сохранённому шагу, если источник всё ещё проверен и доступен.
Если применимой инструкции нет, он уточняет проблему или сообщает о недостатке
сведений. Это также позволяет выйти из ожидания формы, оставшегося после старого
выпуска; вручную менять БД не нужно.

В Talk сбор письма идёт по одному вопросу: после ФИО и текущего компьютера бот
спрашивает **тему**, затем **подробное описание**. Ответ только на вопрос о теме
ещё не создаёт черновик. Для письма описание обязательно; исходная реплика о проблеме
не подставляется вместо нового описания автоматически. Пример обычного диалога:

```text
Бот: Укажите тему письма.
Сотрудник: Уменьшить громкость сканера
Бот: Подробно опишите проблему.
Сотрудник: Проводной сканер громко пищит после каждого считывания.
Нужно уменьшить звук, сохранив подтверждение успешного сканирования.
```

Прежние формы с четырьмя или пятью строками, включая логин, остаются совместимыми,
но логин больше не запрашивается и не выводится. После четырёх строк без описания
бот всё равно спросит описание; пять строк с явно данным описанием могут завершить
сбор сразу. Подписи полей не обязательны. Если сведений недостаточно, бот сохраняет
уже полученные данные и спрашивает одно недостающее поле. Неявные или придуманные
моделью значения не заполняются. Текст описания и переносы строк сохраняются;
описание длиннее 2000 символов нужно сократить самостоятельно.
Пока сбор данных продолжается, исправление можно указать явно, например
`Тема: Уменьшить громкость сканера` или `Описание: ...`. **«Отмена»** и **2**
возвращают к боту и на этапе темы, и на этапе описания.
Черновик не является выгрузкой переписки. Пароли и ключи в форму
не включаются. После подготовки можно написать **«Продолжить с ботом»**.
Эта реплика не отправляет подготовленное письмо.

После предложения выбора **1 / 2** новый технический вопрос своими словами может
вернуть разговор к поиску инструкции. На уже открытом этапе темы или описания текст
остаётся данными письма: он не превращается в новый поиск только потому, что содержит
вопрос. Обычное уточнение текущего шага не считается неудачей всей инструкции.
Подтверждённые успешные инструкции могут ускорять будущий поиск, но поля письма и
персональные данные не сохраняются в таком кэше.

## Фото и подпись к нему

В личный разговор можно отправить фото **JPEG или PNG** вместе с текстовой подписью.
Подпись обрабатывается как обычное сообщение: если бот ждёт подробное описание,
она участвует в заполнении описания и не должна оставаться без ответа. Если данных
недостаточно, бот задаёт один уточняющий вопрос. Фото без подписи получает
подтверждение и просьбу описать проблему словами. Неподдерживаемый формат получает
понятное сообщение вместо молчаливого пропуска.

Это приём вложения, **не распознавание его содержимого**: vision/OCR ещё не настроены.
Бот не читает текст ошибки с изображения и не придумывает увиденные детали.
В БД приложения сохраняются проверенный идентификатор/метаданные сообщения Talk,
подпись и отметка фото; байты входящего изображения автоматически не скачиваются
и не сохраняются. Сам файл остаётся в Nextcloud. Это не меняет прежнюю выдачу
утверждённых иллюстраций из базы знаний.

## Что приходит в Talk

Бот пишет **«Подготовлено письмо для технической поддержки»** и сразу показывает
получателя, тему **`[AI-Support] <тема проблемы>`** без UUID и полный текст письма. Сохраняется
статус `DRAFT`, а не `SENT`; задача автоматической SMTP-отправки не создаётся.
Ранее поставленные в очередь задачи отправки почты в этом режиме не обрабатываются.

Тема остаётся только в заголовке письма с одним префиксом `[AI-Support]`.
В начале тела находится введённое сотрудником подробное описание, а в конце —
ФИО и текущий компьютер. В тело не добавляются повтор темы, «Исходная проблема»,
UUID или текст-заглушка. Например:

```text
Проводной сканер громко пищит после каждого считывания.
Нужно уменьшить звук, сохранив подтверждение успешного сканирования.

ФИО: Павел
Компьютер: terminal76-sk
```

- Для коротких данных ссылка **«Открыть письмо в почте»** использует `mailto:`
  с получателем, темой и заполненным текстом. Предпросмотр и такая ссылка содержат
  один полный текст. Введённое сотрудником форматирование остаётся текстом письма.
- Для длинных данных ссылка открывает получателя и тему. **Полное тело нужно
  скопировать из сообщения бота и вставить в письмо**. Бот явно сообщает об этом;
  описание не сокращается и не заменяется файлом.
- Если даже полная тема слишком длинна для ссылки, в ней остаётся только префикс
  `[AI-Support]`. Тогда скопируйте из сообщения бота **полную тему и полный текст**.
  В видимом черновике они сохраняются целиком.

Письмо показывается только в том же проверенном личном разговоре сотрудника и бота.
Как и остальные данные переписки, текст доступен тем, кто имеет доступ к этому чату.
Если в обращении есть фото, бот явно предупреждает: **прикрепите его к письму вручную**.
Открываемая ссылка `mailto:` передаёт текст, а не файл изображения. Перед отправкой
сохраните нужное фото из Talk/Nextcloud и добавьте его к письму в своём Outlook.
Автоматическое добавление фото пока не реализовано; подготовка письма не означает,
что его вложения уже перенесены.

## Открытие и отправка пользователем

Нажмите **«Открыть письмо в почте»**. Talk или Windows может запросить разрешение
или выбор зарегистрированной почтовой программы. Сам сервер не может автоматически
открыть Outlook на рабочем месте при поступлении сообщения в Talk: стандартный путь
требует нажатия ссылки пользователем. Готовность конкретного Talk Desktop, браузера
и почтового обработчика проверяется на рабочем устройстве. Новая программа или
локальный агент для этого не устанавливается.

Перед отправкой проверьте получателя, тему, описание, ФИО, компьютер и учётную запись
отправителя, а при наличии фото — и прикреплённые файлы. При необходимости исправьте готовое письмо в почтовой программе;
редактирование уже подготовленного preview через бота не реализовано.
Затем **отправьте письмо в техническую поддержку из своего почтового ящика**.
Backend не видит это нажатие и не
подтверждает приём письма почтовым сервером. Не считайте сообщение бота
«черновик подготовлен» подтверждением доставки.

## Автоматическое получение данных Windows

Подготовлен необязательный обработчик `ai-support:`: администратор развёртывает
подписанный локальный скрипт через GPO из `\\srvfile-sk\Distrib\AI_bot\Scripts`.
Используется встроенный Windows PowerShell 5.1, отдельное приложение не устанавливается.
Для передачи нужен внутренний HTTPS callback; UNC-папка служит только источником пакета.
Функция по умолчанию выключена (`DEVICE_COLLECTION_BASE_URL` пуст).
Обновление писем можно установить с выключенным сбором: схема `0009` применяется,
компьютер вводится вручную. Readiness `device_collection_configured` показывает
только наличие адреса, а не готовность приёмника и Windows-пилота.

После включения при неизвестном компьютере бот предлагает одноразовую ссылку.
Сотрудник открывает её на текущем рабочем месте, при необходимости подтверждает
запуск обработчика. Передаётся только имя компьютера; ФИО остаётся из Nextcloud.
Обычная HTTPS-ссылка без предварительной настройки Windows не запускает скрипт.
Незаметный запуск без подтверждений и переключения окна не гарантируется.
Ручной ввод имени остаётся запасным вариантом. Развёртывание, ограничения и проверка:
[получение имени компьютера через GPO](windows-device-collection.md).

Подтверждённый почтовый клиент сотрудников — **Classic Outlook**. Настройка
реального HTTPS-приёмника и расширение помощника для создания черновика с фотографиями
**отложены пользователем**. Текущий Windows-пакет сбора компьютера не создаёт письмо
в Outlook и не добавляет вложения. До отдельного подключения сохраняются `mailto:`,
ручное прикрепление фотографий и отправка из личного ящика. SMTP и `.eml` не включаются.

## Ожидание ответа

Выпуск **0.3.10** сохраняет нативный индикатор **«печатает»** из 0.3.4 через внутренний
signaling или настроенный HPB/WSS с учётом приватности Talk. Новые служебные
сообщения «Готовлю ответ…» и их удаления не создаются; старые отметки удаления
в истории остаются. Если signaling недоступен, основной ответ готовится без индикатора.

Проверка предпосылок без входа в разговор и отправки:

```bash
sudo docker compose exec talk python -m app.talk_worker --check-typing
```

Она показывает настройки, но не доказывает отображение в конкретном Talk Desktop.
Фактическую работу индикатора проверяют новым вопросом в личном разговоре.

## Ручная приёмка

Пока в `SUPPORT_EMAIL` стоит ваш адрес, используйте вымышленные тестовые данные:

1. В текущем личном разговоре напишите **«Оператор»**, затем **1**. Проверьте ФИО
   и компьютер, отсутствие заголовка «Данные профиля Nextcloud» и логина. Неизвестный
   компьютер должен уточняться одним вопросом.
2. Ответьте только на вопрос о теме. Черновик и ссылка почты ещё не должны появиться:
   бот должен отдельно спросить подробное описание. Отправьте JPEG/PNG с подробным
   описанием в подписи: бот должен обработать текст и ответить.
3. Проверьте preview: тема с одним `[AI-Support]` только в заголовке, описание в начале
   тела, ФИО и компьютер в конце; нет повторённой темы, «Исходной проблемы», UUID,
   логина и `.eml`. Бот говорит о подготовленном письме, а не об отправленном.
4. Для короткой формы проверьте ссылку **«Открыть письмо в почте»**. Для длинного
   описания скопируйте весь текст в открытое письмо, включая окончание описания.
5. Если добавляли фото, проверьте предупреждение о ручном прикреплении. Откройте письмо
   в своём Classic Outlook, прикрепите файл сами и проверьте, что он присутствует.
   До вашего нажатия **«Отправить»**
   тестового письма в вашем ящике быть не должно. Отправьте его сами и проверьте приём.
6. В новом случае на этапе темы или описания ответьте **«Отмена»** или **2** и убедитесь,
   что диалог с ботом продолжается без принудительного заполнения формы.
7. Начните другое обращение с другого рабочего места: прошлое имя компьютера
   не должно подставляться. Задайте вопрос о настройке сканера в 1С АДРЕС: проверьте
   штатный индикатор «печатает», ответ и исходные фотографии без новых служебных
   сообщений и отметок удаления. Быстрый ответ может не показать заметный индикатор.
8. Отправьте JPEG/PNG без подписи: должны прийти подтверждение и просьба описать
   проблему словами, без выдуманного распознавания. Проверьте также явный ответ
   на неподдерживаемый формат.

Эта проверка нужна именно с вашим Talk, Windows и почтовым клиентом. Локальные
тесты подготовки ссылки не доказывают, что установленный Outlook откроется.
Адрес службы поддержки меняется позднее тем же локальным
изменением `SUPPORT_EMAIL` и пересозданием сервисов; пользовательский текст его
не переопределяет.

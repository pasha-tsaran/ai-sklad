# Письмо в поддержку: карточка и открытие почты

Режим `MAIL_BACKEND=mailto` не подключает сервер к почтовому ящику и не отправляет
письма автоматически. После заполнения формы бот готовит письмо с данными обращения
и передаёт его сотруднику в текущем личном разговоре Talk. Сотрудник открывает
черновик в своей почтовой программе, проверяет его и сам нажимает **«Отправить»**.
Файлы `.eml` не создаются и не прикладываются.

SMTP-сервер, логин и пароль для этого режима не нужны. Отправитель выбирается
почтовым клиентом пользователя. Получатель берётся только из серверного
`SUPPORT_EMAIL`, а не из сообщения сотрудника или ответа модели.

## Настройка на Debian

Для уже работающей установки Talk сначала получите опубликованный код и соберите
образы, оставляя действующие контейнеры работать:

```bash
cd /opt/ai-support
git status --short
git pull --ff-only origin main
sudo docker compose build api worker migrate talk
```

При локальных изменениях отслеживаемых файлов или ошибке `pull` сначала разберите
их причину. Не заменяйте действующий `.env` файлом примера.

Включите подготовку писем отдельной командой. Она спросит адрес получателя:

```bash
python3 scripts/configure_mail_drafts.py
python3 scripts/configure_mail_drafts.py --check
```

Для теста введите свой реальный email. Скрипт атомарно сохраняет только два
параметра в существующем `.env`, убирает их дубликаты и оставляет остальные
настройки без изменений. Пароли не выводятся, SMTP не используется:

```dotenv
MAIL_BACKEND=mailto
SUPPORT_EMAIL=your.name@collant.ru
```

`your.name@collant.ru` — образец: **для проверки укажите свой реальный адрес**.
Это адрес получателя черновика, а не пароль и не настройка отправителя.
Он вводится локально на сервере. Остальные строки, особенно PostgreSQL, API,
Open WebUI и Nextcloud, оставьте как есть. Не выводите `.env` целиком в чат.

При ручной настройке эти же строки можно изменить в `nano .env`:
**Ctrl+O**, **Enter**, затем **Ctrl+X**. `--check` только читает настройки
и не открывает сеть или почтовую программу.
Выпуск **0.3.4** оставляет текущую схему **`0006`**, новой миграции нет.
Если `0006` уже применена, после успешной сборки переходите сразу к пересозданию
сервисов ниже. Если сервер ещё на `0005` или более старой схеме, сначала остановите
сервисы приложения и примените миграцию:

```bash
sudo docker compose stop api worker talk
sudo docker compose run --rm migrate
```

Продолжайте только после завершения миграции с кодом `0`. Для уже работающей БД
примените новые настройки только к сервисам приложения:

```bash
sudo docker compose up -d --no-deps --force-recreate api worker talk
curl -fsS http://127.0.0.1:8000/health/ready
sudo docker compose logs --tail=100 talk
```

В readiness ожидается `mail=mailto`. Это показывает выбранный режим, но не
подтверждает работу почтовой программы на устройстве сотрудника. База данных
и её том не пересоздаются. Текущая вершина схемы — **`0006`**; при обновлении с
`0005` миграцию нужно выполнить. Обновлять Open WebUI, переустанавливать
Tool/Filter, менять системный промпт или загруженные инструкции не требуется.

## Выбор в разговоре

Когда пользователь просит специалиста или подтверждённого решения недостаточно,
бот предлагает варианты:

- **1** — оформить письмо в техническую поддержку.
- **2** — продолжить диалог с ботом.

После выбора **1** бот показывает карточку с **ФИО и компьютером**. Имя берётся
из проверенного профиля участника текущего личного разговора Nextcloud, а не
считывается из Windows. Проверьте ФИО и при необходимости исправьте его.
Заголовок «Данные профиля Nextcloud» и логин не включаются ни в карточку,
ни в письмо. Внутренний ID используется только для привязки к проверенному сотруднику.

Компьютер подставляется только из явного сообщения сотрудника **в текущем обращении**.
Имя из прошлой заявки не переносится: рабочее место может измениться. Если актуального
имени нет, карточка показывает **«Не определён»**, и бот задаёт один вопрос об
используемом сейчас компьютере. Например, можно ответить `terminal76-sk`.
Обычный Talk API не передаёт имя компьютера Windows; IP, имя Debian и догадка
модели его не заменяют. Сам выбор поддержки ещё не создаёт и не отправляет письмо.
В ожидании формы можно написать **«Отмена»** или **«2»**. Бот снимает ожидание формы
и возвращается к сохранённому шагу, если источник всё ещё проверен и доступен.
Если применимой инструкции нет, он уточняет проблему или сообщает о недостатке
сведений. Это также позволяет выйти из ожидания формы, оставшегося после старого
выпуска; вручную менять БД не нужно.

Данные можно написать обычным текстом без названий полей:

```text
Меня зовут Павел, компьютер terminal76-sk.
Нужно настроить сканер ШК и уменьшить громкость на проводном сканере.
```

Прежние формы с четырьмя или пятью строками, включая логин, остаются совместимыми,
но логин больше не запрашивается и не выводится. Старые подписи полей
остаются допустимыми. Если сведений недостаточно, бот сохраняет уже полученные
данные и спрашивает только одно недостающее поле. Неявные или придуманные
моделью значения не заполняются. Описание необязательно.
Черновик содержит заполненные поля и исходную проблему;
его не следует считать полной выгрузкой всей переписки. Пароли и ключи в форму
не включаются. После подготовки можно написать **«Продолжить с ботом»**.
Эта реплика не отправляет подготовленное письмо.

## Что приходит в Talk

Бот пишет **«Подготовлено письмо для технической поддержки»** и сразу показывает
получателя, тему **`[AI-Support] <тема проблемы>`** без UUID и полный текст письма. Сохраняется
статус `DRAFT`, а не `SENT`; задача автоматической SMTP-отправки не создаётся.
Ранее поставленные в очередь задачи отправки почты в этом режиме не обрабатываются.

- Для коротких данных ссылка **«Открыть письмо в почте»** использует `mailto:`
  с получателем, темой и заполненным текстом. Предпросмотр и такая ссылка содержат
  один полный текст. Введённое сотрудником форматирование остаётся текстом письма.
- Для длинных данных ссылка открывает получателя и тему. **Полное тело нужно
  скопировать из сообщения бота и вставить в письмо**. Бот явно сообщает об этом;
  описание не сокращается и не заменяется файлом.
- Если даже полная тема слишком длинна для ссылки, в ней остаётся только префикс
  `[AI-Support]`. Тогда скопируйте из сообщения бота **полную тему и полный текст**.
  В видимом черновике они сохраняются целиком.

Письмо показывается только в том же проверенном личном разговоре сотрудника и бота.
Как и остальные данные переписки, текст доступен тем, кто имеет доступ к этому чату.

## Открытие и отправка пользователем

Нажмите **«Открыть письмо в почте»**. Talk или Windows может запросить разрешение
или выбор зарегистрированной почтовой программы. Сам сервер не может автоматически
открыть Outlook на рабочем месте при поступлении сообщения в Talk: стандартный путь
требует нажатия ссылки пользователем. Готовность конкретного Talk Desktop, браузера
и почтового обработчика проверяется на рабочем устройстве. Новая программа или
локальный агент для этого не устанавливается.

Перед отправкой проверьте получателя, тему, поля формы и учётную запись отправителя.
Затем самостоятельно нажмите **«Отправить»**. Backend не видит это нажатие и не
подтверждает приём письма почтовым сервером. Не считайте сообщение бота
«черновик подготовлен» подтверждением доставки.

## Ожидание ответа

Выпуск **0.3.4** использует нативный индикатор **«печатает»** Talk через внутренний
signaling или настроенный HPB/WSS с учётом приватности Talk. Новые служебные
сообщения «Готовлю ответ…» и их удаления не создаются; старые отметки удаления
в истории остаются. Если signaling недоступен, основной ответ готовится без индикатора.

Проверка предпосылок без входа в разговор и отправки:

```bash
sudo docker compose exec talk python -m app.talk_worker --check-typing
```

Она показывает настройки, но не доказывает отображение в конкретном Talk Desktop.
Фактическую работу индикатора проверяют новым вопросом в личном разговоре.

## Ручная приёмка

Пока в `SUPPORT_EMAIL` стоит ваш адрес, используйте вымышленные тестовые данные:

1. В текущем личном разговоре напишите **«Оператор»**, затем **1**. Проверьте ФИО
   и компьютер, отсутствие заголовка «Данные профиля Nextcloud» и логина. Неизвестный
   компьютер должен уточняться одним вопросом.
2. Убедитесь, что бот говорит о черновике и не утверждает, что письмо отправлено.
   Проверьте тему с префиксом `[AI-Support]`, полный текст и отсутствие `.eml`.
3. Для короткой формы проверьте ссылку **«Открыть письмо в почте»**. Для длинного
   описания скопируйте весь текст в открытое письмо, включая окончание описания.
4. Откройте черновик в клиенте на рабочем устройстве. До вашего нажатия **«Отправить»**
   тестового письма в вашем ящике быть не должно. Отправьте его сами и проверьте приём.
5. В новом случае на этапе формы ответьте **«Отмена»** или **2** и убедитесь,
   что диалог с ботом продолжается без принудительного заполнения формы.
6. Начните другое обращение с другого рабочего места: прошлое имя компьютера
   не должно подставляться. Задайте вопрос о настройке сканера в 1С АДРЕС: проверьте
   штатный индикатор «печатает», ответ и исходные фотографии без новых служебных
   сообщений и отметок удаления. Быстрый ответ может не показать заметный индикатор.

Эта проверка нужна именно с вашим Talk, Windows и почтовым клиентом. Локальные
тесты подготовки ссылки не доказывают, что установленный Outlook откроется.
Адрес службы поддержки меняется позднее тем же локальным
изменением `SUPPORT_EMAIL` и пересозданием сервисов; пользовательский текст его
не переопределяет.
